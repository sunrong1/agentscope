## 3. 8 大核心成果（按价值排序）

### ① Schema Cascade（W4 最有架构感）

**核心洞察**：ModelCard.from_yaml 合并 3 层 schema（基础 / 自动 / 覆盖）——**3 个 actor 3 个 layer 互不耦合**。

**3 大机制**：
1. **Auto-filter**：能力不满足 → pop（如 thinking 不支持 → 删 `thinking_*` 字段）
2. **Auto-inject**：配置需要 → 补（如 `max_tokens.maximum = output_size`）
3. **Parameter override**：用户覆盖（`{**base, **override}` / null=pop / hidden=pop）

**类比**：CSS cascade / Git merge / 环境变量层叠。

**为什么这模式强大**：
- 改开发者 schema → 不影响用户 YAML
- 改框架 capability → 不影响基础 schema
- 改用户 YAML → 不影响前两层
- **3 个 actor 完全解耦**

### ② Validation Responsibility Delegation（W4 最深洞察）

**核心洞察**：不是"信任边界"——**是"上游有谁验"**。

| 数据源 | 上游 validator | 选择 |
|---|---|---|
| LLM API response | ✅ OpenAI SDK | dataclass（委托）|
| YAML 配置 | ❌ 没人 | BaseModel（自己验）|
| HTTP request | ❌ | BaseModel |
| Database read | ❌ | BaseModel |

**Pydantic 真正价值** = **业务约束，不是类型**：
- `status: Literal["active", "deprecated", "sunset"]` —— 必须 3 选 1
- `context_size: int = Field(gt=0)` —— 必须正数
- `datetime | None` —— 必须是 datetime

**vs W3 Q1 升级**：昨天"信任边界"是粗概念——**今天升级为"验证责任委托"**——**更精确、更可操作**。

### ③ Type-Aware Streaming Merge（W4 最实用）

**核心洞察**：流式协议不是"is_last 一个 bool"——**是"每 block 各自的合并语义"**。

| Block type | 合并策略 |
|---|---|
| TextBlock | `text += delta` |
| ThinkingBlock | `thinking += delta` |
| ToolCallBlock | `input += delta`（**JSON 字符串拼接，不解析**）|
| DataBlock (audio) | bytes concat |
| DataBlock (image/video) | **替换** |
| DataBlock (类型不匹配) | 整块替换 |

**流式协议 5 大设计点**：
1. **Chunk vs full** = `is_last: bool`
2. **Block-level 累加** = `content: list[Block]`
3. **顺序保持** = append not replace（除 image）
4. **Usage 累加** = `usage.input_tokens += event.input_tokens`
5. **终止信号** = `is_last=True` + `finished_reason` 双信号

**对 LLM Streaming API 设计的普适性**：这套模式**任何流式协议都能用**——**audio streaming / video streaming / WebSocket / SSE 全部适用**。

### ④ Field Grouping = Access Pattern Grouping（W4 最实战）

**核心洞察**：Msg 字段分 3 组不是装饰——**是访问模式分组**：

| 组 | 问什么 | 消费者 |
|---|---|---|
| **Context** | "说了什么" | LLM |
| **Metadata** | "什么时候 / 多少 token" | 监控 |
| **Workflow** | "走到哪一步" | agent framework |

**判断标准**：
- 3 种不同的访问者 → 3 组
- 1 种访问者 → 1 组足够
- 字段经常一起读写 → 同一组

**vs "全部塞一块"**：混在一起——**想加 metadata 时不知道放哪**——**每次都 new 一个字段**——**混乱**。

### ⑤ Strategy Pattern for Block routing（W4 最 OOP）

**核心洞察**：8 种 block 用 Union Type 表达——**不是继承**。

```python
ContentBlock = Union[
    TextBlock, ThinkingBlock, DataBlock,
    AudioBlock, ImageBlock, VideoBlock,
    ToolCallBlock, ToolResultBlock,
]
```

**为什么不是继承**：
- 继承强制共享父类属性——**8 种 block 字段差异巨大**
- **Union + Literal discriminator**——**type-safe + open extension**
- **"真正的 OO 是 Literal Type Union"**——**不是 class 继承**

### ⑥ Two State Machines for One Lifecycle（W4 最深）

**核心洞察**：HITL 2.0 的 reentrant 协议——**两个状态机管一个生命周期**：

```
Pre-execution FSM:  ToolCallState (None → ALLOWED → ASKING → SUBMITTED)
Post-execution FSM: ToolResultState (None → RUNNING → SUCCEEDED/FAILED)
```

**Q5 bug 起源**：两个 FSM transition 没考虑周全——pre FSM 转 SUBMITTED 时 post FSM 不认识。

### ⑦ Big Method OK if Cohesive（W4 最反直觉）

**核心洞察**：SRP 不是"方法要短"——**是"1 个方法 1 个理由改"**。

`Msg.append_event` 1 个方法 15+ case——**所有 case 改 = Event 协议变化**——**1 个理由**——**聚合合理**。

**判断标准**：
- 改 1 个 case 时其他 case 也要改？→ 聚合
- 改 1 个 case 时其他 case 不用改？→ 拆分

**vs W3 "Duplication > Wrong Abstraction"**：W3 那个例子是 3 个 middleware 函数不抽——**W4 这个例子是 15+ case 不拆**——**同一个原则的不同应用**。

### ⑧ Factory Function for Role-Only Variants（W4 最简洁）

**核心洞察**：`UserMsg` / `AssistantMsg` / `SystemMsg` 是 `def` 不是 `class`——**不是 OOP 的"次品"**——**是 Discriminated Union**：

```python
def UserMsg(name, content, ...) -> Msg:
    return Msg(name=name, content=..., role="user", ...)
```

**判断标准**：
- 子类有**额外属性**？→ class 继承
- 子类只是**不同 role**？→ factory

**UserMsg 没额外属性**——**factory 完美**。
