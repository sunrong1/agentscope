### Q1（transformer vs chain）✅✅ 强

**你答**："transformer 固定顺序 / chain 决策可跳过"

| 模式 | 数据流 | 适用 |
|---|---|---|
| **Transformer (pipeline)** | `result = A(result); B(result); C(result)` | **每个必须跑** |
| **Chain (recursive)** | `mw.on_xxx(next=...)` | **可决策**——**可跳过**——**可短路** |

**`_get_system_prompt` 用 transformer 因为**：
- 系统提示**每个 middleware 都要改**——**不能"跳过"**——**所有规则都要应用**

**`_compress_context` / `_reasoning` / `_acting` 用 chain 因为**：
- middleware 可能"不改"——**也可能直接跳到 impl**（"我不改你的，但你可以执行"）

**架构师视角**：
> **"Transformer = pipeline (always run)"**——**不可控**
> **"Chain = policy (may skip)"**——**可控**
> - **判断标准**：你的 middleware 是"必须改"？→ transformer / "可改可不改"？→ chain

### Q2（dict vs typed）⚠️ 浅

**你答**："dict 灵活 / typed 要定义"

**更深**——**为什么 model input 适合 dict**：

| 维度 | dict | typed |
|---|---|---|
| **类型安全** | 运行时检查 | 编译时检查 |
| **IDE 补全** | ❌ | ✅ |
| **改动成本** | 改 key | 改 dataclass |
| **provider 适配** | 任意 shape | 必须先定义 |

**AgentScope 选 dict 因为**：
- 不同 model provider（OpenAI / Anthropic / Qwen）**对 input shape 略有不同**
- Anthropic 可能有 `system` 是单独字段
- OpenAI 用 `messages` 全包含
- **dict 让 framework 不绑定到某个 provider**

**架构师视角**：
> **"Dict 输出 = 'protocol boundary'"**——**agent 层和 model 层之间**
> - agent 层只负责**生成** messages 和 tools
> - model 层负责**翻译**到 provider 协议
> - **中间用 dict**——**两边都不绑死**

**vs 真正 typed 适合的场景**：
- 内部核心数据结构（`ToolCallBlock`）——**用 pydantic**（稳定 + validate）
- 跨 provider boundary（`messages` / `tools`）——**用 dict**（多变）

**Framework 设计原则**：**"边界用 dict，内部用 typed"**

### Q3（双重容错）✅✅ 强

**你答**："网络波动重试 / 模型挂切模型"

| 错误类型 | 例子 | 处理 |
|---|---|---|
| **Transient** | network blip / rate limit / timeout | **retry**（等几秒再试）|
| **Persistent** | model broken / auth failed / bad request | **fallback**（换模型）|

**为什么不只 retry**：
- model 永久挂——retry 100 次也挂

**为什么不只 fallback**：
- 网络 blip（瞬时失败）——**fallback 启动多余**——**浪费 fallback 模型**

**架构师视角**：
> **"Layered resilience"**——**每一层处理不同类型的错误**
> - **Retry = recover from transient failures**
> - **Fallback = recover from persistent failures**
> - **Both = handle all failure modes**

**AgentScope 策略**：
- 每次调用先 retry 几次
- retry 全失败才 fallback
- fallback 也失败才 raise
